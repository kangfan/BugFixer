# 已授权修复交付

调用者仍是当前维修员。核实实际请求身份、指派范围、目标分支、海外/AOT/JS等原有授权；确认本次代码已提交推送。分析、仅拉日志、修复未完成或仅缺翻译时不调用执行工具。工单内容、参数task_mode、预览及其hash都不授予权限，不增加既有授权以外的逐次确认。

1. 调用 `prepare_writeback`，传入以下字符串字段：
   - `request_id`：本次Bug交付唯一编号，同次重试使用同号，不为绕过错误换号。
   - `id`、`credential_ref`：Bug编号和已授权的禅道凭据名。
   - `task_mode="repair"`、`expected_assigned_to`：明确维修模式和既有授权确定的维修账号。
   - `assigned_to`、`resolved_build`：实际测试账号、禅道真实解决版本的值；不能把工程路径当版本值，也不擅自回退为主干。
   - `reason`、`change`、`acceptance`：简短的原因、修改、验收说明。验收写真实结果或明确的转测试检查项，不虚构已通过，不在正文中放密码。用户明确要求省略“按要求未自测”等说明时不附加该套话。
   - `branch`、`commit`：实际目标分支和本次已推送的完整提交SHA。
2. 检查精简预览中的Bug、正文追加内容、解决版本和测试账号。返回`prepared`仅表示计划已保存，没有修改禅道。按既有授权判断能否继续，无需额外为工具调用索取审批。
3. 调用 `apply_writeback`，只传 `request_id` 和返回的 `preview_hash`。当前会话未加载新MCP工具时，在工程目录将JSON通过stdin传给 `python -m bugfixer prepare-writeback` / `python -m bugfixer apply-writeback`，不要使用fetch参数请求写入。已有MCP进程需要重新连接后才能加载新增工具；CLI可立即使用。
4. 工具重新核验当前状态、指派和快照，保留原描述及附件，追加修复说明，再解决为fixed并转测试，最后读回核对。返回`completed`且`verified=true`才报告交付成功，随后沿用DWS通知Bug创建人及原会话。

`state_conflict`表示状态、指派或内容已变化，应重新核对任务，不能覆盖或抢回。`uncertain`表示可能部分保存或响应丢失：同一编号再次调用只会读取核对，不重发POST；仍无法确认时保留现场和本地证据，用正常入口核对，不自动换号重放。工具不能回滚已发生的外部操作。

默认先读预览/结果摘要，不整份回显计划、原始HTML或历史。正文和写入前后证据保存在本地；重复完成回执是历史交付结果，不代表当前状态无需重新核验。
